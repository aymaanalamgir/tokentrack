# Agent optimization: comparisons, anomalies and explainable insights

Slice 9B turns the descriptive agent telemetry of Slice 9A into deterministic, evidence-backed findings. Nothing here is generated by a language model, nothing is predicted, and no finding states a cause. Metric definitions are those in [agent efficiency metrics](agent-efficiency-metrics.md).

## Ownership

| Layer | Owns |
| --- | --- |
| Kotlin `AgentInsights` / `InsightRules` / `Periods` | Comparison windows, per-period operational metrics and rates, trend buckets, model/token breakdown, operational findings, every threshold, hypothetical rate-only re-rating from pricing snapshots |
| Kotlin `AgentAnalytics.cohort` | Keyset pages (at most 1,000 runs) of the authorized run cohort |
| Rails `Agents::Scope` | The population (tenant, managed users, led projects) and filter validation |
| Rails `Agents::CostAggregator` / `LedgerCosts` | Corrected posted ledger cost per run, folded into per-agent, per-bucket and per-model sums |
| Rails `Agents::Insights` / `InsightText` | Cost-based findings, cost-driver breakdown, financial coverage qualification, wording, final response |
| Next.js | Rendering, filters, drill-down links, identity-keyed caching |

Rates and per-run token metrics are computed only in Kotlin. Cost-derived metrics are computed only in Rails. The UI formats values; it computes neither.

## Comparison windows

All windows are UTC and half-open. `compare` selects the mode:

| Mode | Current | Comparison |
| --- | --- | --- |
| `previous_period` (default) | `[start, end)`; without dates, the 14 days ending the day after the last recorded run | The equal-length window immediately before |
| `week` | The Monday week containing the anchor | The previous Monday week |
| `month` | The calendar month containing the anchor | The previous calendar month |

The anchor is `end`, capped at the day after the last recorded run, so simulated demo dates work regardless of the wall clock. If the current week or month is incomplete, the response sets `partial_current_period` and compares the **equivalent elapsed portion** of the previous period (`comparison_basis: equivalent_elapsed_portion`), never a partial period against a full one. A comparison period with no runs yields `unsupported_comparison`, a null percentage and no finding.

## Thresholds

Defined once, in `tokentrack.agent-insights` in the usage engine's `application.yml` (`InsightThresholds`). Kotlin returns them in every response; Rails applies the cost thresholds from that response and the UI displays them. They are demonstration defaults, not statistical significance tests.

| Setting | Default | Used for |
| --- | --- | --- |
| `min-runs` | 20 per period | Minimum sample for a definitive finding |
| `min-runs-limited` | 8 per period | Below this, no comparison at all |
| `retry-rate-increase-points` | 10 | Retry rate, percentage points |
| `success-rate-decrease-points` | 10 | Success rate, percentage points |
| `tokens-per-run-increase-percent` | 30 | Input and output tokens per run |
| `duration-increase-percent` | 30 | Median completed-run duration |
| `cost-per-success-increase-percent` | 25 | Corrected cost per successful run |
| `model-cost-share-percent` | 70 | One model's share of an agent's corrected cost |
| `failed-run-cost-share-percent` | 20 | Share of corrected cost on failed runs |
| `critical-multiplier` | 2 | A change of at least twice its threshold is `critical` |

## Findings

| Type | Rule | Sample basis |
| --- | --- | --- |
| `retry_increase` | Retry rate rose by the threshold in points; from recorded attempts only | Runs |
| `success_rate_decline` | Success rate fell by the threshold in points; running/unknown runs excluded | Concluded runs |
| `input_token_spike`, `output_token_spike` | Tokens per run rose by the threshold percent | Runs with linked usage |
| `duration_increase` | Median duration rose by the threshold percent (median resists a few extreme runs) | Completed runs |
| `cost_per_success_increase` | Corrected cost per success rose by the threshold percent | Runs, plus cost coverage |
| `failed_run_spend` | Failed runs' share of current corrected cost at or above the threshold | Current runs |
| `model_cost_concentration` | One model's share of current corrected cost at or above the threshold, only when the agent has at least two costed models; always `info` | Current runs |
| `pricing_coverage_gap` | The agent has unpriced or undelivered usage in the current period | Not sampled |

Run volume has no rule. More runs at an unchanged cost per run produce no finding.

## Evidence quality

| State | Meaning | Effect |
| --- | --- | --- |
| `sufficient` | Both periods meet `min-runs` and, for cost findings, cost coverage is complete | `warning` or `critical` |
| `limited_sample` | Both periods have at least `min-runs-limited` but one is below `min-runs` | Reported as `info` with the counts |
| `incomplete_cost_data` | Some linked usage is unpriced or undelivered | Cost findings reported as `info`, based on known posted cost only |
| `insufficient_data` | A period has fewer than `min-runs-limited` runs | No finding; the agent is listed under "Not compared" with the reason |
| `unsupported_comparison` | A period has no runs | No finding, no percentage |

There is no numeric confidence score.

## Cost-driver breakdown

For each agent with runs in both periods, `decomposition` contains:

- **Exact split.** `volume_effect = (current runs − baseline runs) × baseline cost per run`; `per_run_cost_effect = cost change − volume_effect`. The two sum to the ledger cost change by construction.
- **Associated factors.** Runs, input and output tokens per run, retry rate, success rate, cost of failed runs, and financial corrections, each with baseline, current and change. They are marked `associated`: per-run factors interact, so none is assigned a dollar amount.
- **Model mix.** Each model's share of tokens and its corrected cost in both periods, and whether its pricing rate schedule differed between them.
- **Basis.** `complete_corrected_ledger_cost`, or `known_posted_cost_only` when coverage is incomplete.

## Financial coverage and savings scenarios

Cost is corrected posted ledger expenditure: original run-linked charges plus their correction descendants. A run with no posted receipt contributes nothing and is not counted as zero-cost evidence; `cost_completeness` reports `complete`, `partial_unpriced_or_unposted` or `no_linked_usage` per agent and period.

Retries carry no savings estimate: tokens and cost link to runs, not attempts, so `failed_retry_attempts` cost is reported as unavailable.

The only monetary scenario is the **hypothetical rate-only comparison** attached to a model-concentration finding. Kotlin re-rates the model's recorded priced tokens (same input, cached-input and output counts) under the cheapest other published, non-synthetic schedule on the same pricing tier. It is modeled from pricing snapshots, is not ledger expenditure, and lists what it ignores: model behaviour, quality, success and retry rates, latency, unsupported provider fees and tokenization. If no cheaper same-tier schedule exists the scenario says savings are unavailable.

## Cohort size

The former 5,000-run limit is removed. Rails walks `POST /internal/v1/agent-cohort` in keyset pages ordered by `(started_at, id)`, prices each page with one query that joins two text arrays to the `receipts_agent_run_link` index, and keeps only fixed-size sums. Memory is one page plus per-agent, per-bucket and per-model totals. If the walk cannot finish the request fails with 503; it never returns a partial total. Run lists stay paginated at 100.

Run-linked cost is now attributed to the run by its start time. Slice 9A additionally required each usage event's own timestamp to fall inside the report window, which could drop the cost of a run that straddled the window end while still counting its tokens.

## API

`GET /api/v1/agents/insights` (session cookie, `AccessPolicy` scope, `no-store`). Optional scalar string filters; unknown or malformed ones return 400, entities outside the requester's scope return 404, usage-engine failure returns 503.

| Parameter | Meaning |
| --- | --- |
| `start`, `end` | Both or neither; ISO-8601 UTC, range at most 366 days |
| `compare` | `previous_period`, `week`, `month` |
| `agent_id`, `project_id`, `user_id`, `workflow_type` | Narrow the population (always intersected with scope) |
| `insight_type`, `severity`, `evidence_quality` | Filter the returned findings; `summary.total_findings` still counts all |

Response keys: `schema_version`, `analysis_version`, `currency`, `compare`, `current_period`, `comparison_period`, `partial_current_period`, `comparison_basis`, `trend_bucket`, `scope`, `summary`, `insights`, `agents`, `trend`, `coverage`, `thresholds`, `limitations`, `money_basis`. Money and rates are decimal strings or null.

Each insight has `id`, `type`, `agent_id`, `agent_name`, `agent_key`, `severity`, `status`, `metric`, `unit`, `baseline`, `current`, `absolute_change`, `percent_change`, `threshold`, `sample_size`, `evidence_quality`, `quality_reason`, `financial_coverage`, `evidence`, `associated`, `finding`, `suggested_action`, `limitation`, `time_window`, `comparison_window` and `drilldown` (filters for `GET /api/v1/agents` that list the supporting runs). `GET /api/v1/agents` gains the `retried=true|false` filter for that drill-down.

Insights are computed on demand and not stored, so they cannot go stale.

Internal Kotlin endpoints `POST /internal/v1/agent-insights` and `/internal/v1/agent-cohort` use the analytics bearer credential and the same exact-key body as `agent-analytics`, plus `compare`, or `after_started_at`, `after_id`, `batch` (1–1000) and `bucket`. Neither is reachable through the Next.js proxy.

## Authorization

Every number is aggregated from the population Rails derives from `AccessPolicy`: the whole tenant for an organization viewer; otherwise the requester's own runs, runs by people they manage, and runs in projects they lead. An employee's view of a shared agent is therefore computed from their own runs only. Responses contain no contributing-user lists. An `agent_id` with no runs in the requester's population returns 404. Ledger cost is filtered by the same scope a second time in Rails.

## Known limitations

- Findings are comparisons of two periods. They do not establish cause, and thresholds are not significance tests.
- No attempt-level token or cost linkage exists, so retries cannot be costed.
- Coverage counts priced and delivered events from Kotlin; a delivered receipt that Rails holds as unresolved would still read as complete here. The demo has none (`unresolved_charge_owner: 0`).
- Cohort pages are separate read snapshots; a run imported mid-walk can be missed until the next request.
- Up to 400 agent-period rows per request; a larger population fails with 400 rather than truncating.
- Performance was measured on the local demo dataset and a 6,200-run test cohort only.
